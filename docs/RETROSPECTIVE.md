# Implementation retrospective — 2026-11-02

TripSync AI implements the three PRD §6 epics on one Python/FastAPI application with native WebSockets, PostgreSQL and a React JavaScript client. The user selected local Qwen2.5 1.5B inference and an Indian Bengaluru/INR/IST baseline. Earlier immutable EUR trips/data retain their values. The application has no affiliation with Airbnb and no booking, payment or live travel integration.

The important architectural choices were server-authoritative per-room memory; explicit CAS conflicts instead of silent overwrites; volatile drag acknowledgements with a later committed watermark; and durable significant transitions. Shared authorization/domain services let HTTP and sockets enforce the same membership rules. Exact integer split arithmetic, pre-generation hard filters and canonical source validation remain independent of model output. These choices made failure tests and backup reconciliation more useful than cosmetic success demonstrations.

All required product epics remain in scope; dataset and model complexity were kept small. The six-place destination catalog is fictional. The hybrid recommender uses actual self-generated interactions in the app and a separate frozen synthetic evaluation. Its easy category cohorts produce no demonstrated improvement over content alone; Precision@5 on this fixture is not evidence of real traveler relevance. Provisional voting, Leader-absence and budget defaults remain explicitly provisional.

Phase 4 exposed a concrete operational failure: Ollama was initially stopped, then cold requests repeatedly cancelled model loading at the application deadline. The first full suite therefore failed its actual-model test, and an unpreloaded profile produced only correctly labeled grounded fallbacks. Preloading still left generation too slow: a diagnostic took 10.19 seconds for redundant ID/reason output. Compact source-ID generation and smaller already-filtered context reduced a direct diagnostic to 2.05 seconds; 99/100 measured warm application requests then produced real grounded answers, P95 1.60 seconds, with one disclosed fallback. Extending application deadlines or counting fallback as inference would have hidden the problem. Cold availability and rendered-P95 evidence remain limitations; a single rendered browser answer including automation overhead took 3.20 seconds. Retained samples and final outcomes are in PHASE_4_EVIDENCE.md.

A clean npm reinstall also encountered Windows locks from running Vite/native Rollup/esbuild modules. Dependencies were restored, then a separate directory reproduced `npm ci` without touching a live dependency tree. Fresh Python installation used a separate virtual environment and the exact lockfile; database migrations/tests used newly generated disposable databases. These are automated reproductions on one machine, not a second person's independent setup or a second OS certification.

The largest remaining limits are one application worker, explicitly lossy volatile edits on a crash, local/private hosting, and narrowly measured workloads. Ten socket connections with five distinct identities in two rooms do not establish capacity for fifty distinct planners. Browser paint observations are separate from socket aggregate application, and dispatch-to-all application is only a conservative fan-out proxy. Short warmup and background local verification activity limit benchmark generality. Cold model fallback is an availability limitation even when its response meets a latency deadline. See the evidence for actual target outcomes; no unmeasured target is accepted by implication.

With more time, the priorities are sustained mixed pin/move/lock/vote browser/LAN workloads with clock calibration, more difficult independent recommendation labels, measured model startup/availability improvements, and an operator-managed backup/retention procedure. Multiple workers would require a deliberate room-ownership redesign. Broader public-hosting hardening, unbounded dashboards/long-history pagination, automated idempotency retention cleanup, and richer telemetry are extensions rather than claims about this local prototype.


## Submission follow-up — 2026-11-03

The side quests added active-destination selection, a separate-room flow for a different destination and user-entered personal activities. Goa supplies a second fictional Indian destination. Personal costs use the existing integer budget engine and persist through the room actor. Venue voting and Concierge location anchors retain their catalog source requirement because personal entries have no verified location or venue metadata.

Review exposed a documentation problem. Early plans and later acceptance notes shared the same reference pages, leaving contradictory contracts and proposed tables visible as current. The submission now uses actual migration columns, a current architecture overview and REST/socket examples validated against request models. Historical phase evidence retains the sequence of implementation and measured limits.

The browser follow-up found that the destination select needed an explicit accessible label. After correction, two independent Chrome contexts exercised personal activity synchronization, moving an activity, separate Goa room creation and original-room reload/rejoin. More extensive personal-activity lifecycle and failure coverage would strengthen the follow-up beyond the shared board service's existing regression suite.
